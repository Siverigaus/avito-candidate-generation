# Авито: кандидатогенерация для категории «Услуги»

По короткому поисковому запросу («автоподбор», «баня на дровах») отобрать из корпуса 189 тыс. объявлений
до 50 кандидатов так, чтобы в них попали объявления, выбранные пользователем. Метрика — Recall@50.

**Результат на платформе: Recall@50 = 0.876.** Локальная валидация: 0.942 (первый этап без ранкера 0.915, потолок кандидатов 0.982).

Разрыв между валидацией и платформой: запросы бенчмарка длиннее (3.2 слова против 2.5), реже содержат фильтры (37% против 64%) и чаще ищут по региону (17% против 14%). Валидация из train смещена к частым коротким запросам. Следующий шаг — стратифицировать валидацию и обучение ранкера под распределение бенчмарка.

## Как запустить

```bash
pip install -r requirements.txt
# положить train.parquet, benchmark_items.parquet, benchmark_queries.parquet в папку dataset/
jupyter nbconvert --to notebook --execute solution.ipynb   # или открыть и выполнить все ячейки
# альтернатива без ноутбука (тот же пайплайн):
python src/run.py dataset answer.csv
```

Прогон занимает ~40 минут на 2 ядрах CPU и требует ~6 ГБ RAM. GPU и интернет не нужны.

Воспроизводимость: seed'ы фиксированы, сортировки стабильные, у LightGBM стоят `deterministic=True`, `force_col_wise=True`
и `num_threads=2`. Параметр `force_col_wise` добавлен после отправки: без него LightGBM выбирал режим построения
по замеру скорости, и два прогона расходились примерно на 2% объявлений в ответах (≈49 из 50 совпадают).
Отправленный `answer.csv` получен версией до этого исправления.

## Описание решения

### Данные и признаки

* **Запрос:** текст, локация поиска, текстовые фильтры (`search_infm_params_text`).
  Флаг доставки почти всегда равен 0, категория поиска у всех 114/0, поэтому оба не используются.
* **Объявление:** заголовок, параметры, описание (текстовые каналы), локация и координаты (гео-сигналы),
  подкатегория (сопоставление с запросом), рейтинг, число отзывов, цена.
* **Train (497 тыс. пар «запрос → выбранное объявление»)** используется как источник статистик, а не как база
  для поиска: с корпусом пересекается только ~10% объявлений.

Что показал анализ данных:

1. **Локация — главный сигнал.** 83% выборов сделаны в той же локации, где искали. При этом у части запросов
   локация поиска — регион или вся страна, и в ней самой объявлений нет. Поэтому используется выученное
   распределение P(локация объявления | локация поиска), а не жёсткий фильтр.
2. **Слова запроса часто не совпадают со словами объявления** («уроки вождения» → «Автоинструктор»). Зато в train
   есть сотни тысяч пар «запрос → подкатегория», и 99% корпуса лежит в подкатегориях, которые встречаются в train.
3. **Только 37% текстов запросов бенчмарка встречались в train** — это учтено в валидации.

### Модели и алгоритмы

**Этап 1 — отбор ~300 кандидатов** из всего корпуса по сумме сигналов:

* BM25 по заголовку, параметрам и описанию; стемминг Snowball (ru/en), ё→е;
* BM25 по «расширению документа»: к объявлению приписываются запросы из train, по которым его выбирали;
* символьные 3–4-граммы заголовка (TF-IDF): опечатки и склейки;
* `A · log P(item_loc | search_loc)`, сглаженная по расстоянию: `+ G·exp(−d / 30 км)`, где d — расстояние
  от центра локации поиска до объявления;
* `C · log P(microcat | запрос, фильтры)` — TF-IDF (уни- и биграммы) + логистическая регрессия (SGD) на train.

К ним добавляются top-30 по чистому тексту и объявления, которые выбирали по точно такому же запросу в train.

**Этап 2 — LightGBM lambdarank** по ~40 признакам: скоры каналов и их ранги, расстояние, покрытие запроса
заголовком и фильтров параметрами, рейтинг и отзывы, а также признаки относительно других кандидатов запроса
(отрыв от лучшего кандидата, ранги). Итог — top-50 по скору ранкера.

### Как проверялось качество

Валидация строится из train и повторяет условия теста:

* единица — «поиск» (текст, локация, фильтры); релевантные — выбранные объявления, **которые есть в корпусе
  бенчмарка**; поиск идёт по тому же корпусу из 189 тыс. объявлений;
* для 45% отложенных поисков из обучающей части удаляются все строки с тем же текстом. Иначе «знакомых» запросов
  было бы 87%, а в бенчмарке их 37%;
* для 70% отложенных объявлений удаляется их история в train, потому что в корпусе знакомы train только ~10% объявлений;
* 15 000 отложенных поисков разбиты на 3 фолда, статистики этапа 1 для каждого фолда считаются без него.
  Итоговая оценка: ранкер на фолдах 1–2, метрика на фолде 0.

Абляция первого этапа (без ранкера, 1 500 запросов фолда 0):

| Этап 1 | Recall@50 |
|---|---|
| только текст (BM25 + char n-граммы) | 0.279 |
| + P(item_loc \| search_loc) | 0.872 |
| + P(microcat \| запрос, фильтры) | 0.900 |
| + гео-сглаживание | 0.899 |

Гео-сглаживание почти не меняет top-50 первого этапа, но поднимает долю релевантных среди ~300 кандидатов
(на отдельном прогоне с 0.964 до 0.974), и его выигрыш реализует ранкер через признак `dist_km`.

Итог на полном фолде 0 (5 000 запросов):

| | Recall@50 |
|---|---|
| этап 1 | 0.915 |
| этап 1 + LightGBM-ранкер | **0.942** |
| потолок кандидатов | 0.982 |

### Ошибки и что с ними сделано

Что происходит с релевантными объявлениями фолда 0: 93.9% попадают в top-50, 4.4% есть среди кандидатов,
но ранкер ставит их ниже 50-го места, 1.7% не попадают в кандидаты. Промахов больше, если объявление лежит
в другой локации, чем искали (16.6% против 3.9%), и если текст запроса новый (6.5% против 5.1%).

| Тип ошибки | Решение |
|---|---|
| Кандидаты из других городов | P(item_loc \| search_loc) из train |
| Поиск по региону или стране, объявления в городах внутри | то же распределение вместо фильтра «локация = локация» |
| Соседний город, пары локаций нет в train | сглаживание по расстоянию, признак `dist_km` |
| Нет общих слов у запроса и объявления | классификатор подкатегории, расширение документа запросами из train |
| Опечатки («бобкет» → «Бобкат») | символьные n-граммы |
| Сотни равноценных объявлений по массовому запросу («маникюр» в Москве) | ранкер с относительными признаками и сигналами качества; это основной остаток ошибок |
| Перефразы без общих слов («root права» → «разблокировка смартфона») | не решено; следующий шаг — дообученный bi-encoder |
